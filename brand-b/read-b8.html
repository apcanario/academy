The window: two Anthropic pages disagree

B1 §1 built the course on a 200K-token window on claude.ai, a fifth of the API's 1M. On 2 November 2026 Anthropic's pages say two things.

Where sources disagree. Understanding usage and length limits still says "Claude's context window size is 200K tokens across all models and paid plans", with 500K on some models for Enterprise; the page shows no date (article 11647753, read 2 Nov 2026). How large is the context window on paid Claude plans?, labelled "Updated this week", gives a table for Claude chat in which Fable 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Sonnet 5 and Haiku 5.5 have 1M tokens, Fable 5, Opus 4.6 to 4.8 and Sonnet 4.6 have 500K, and "Outside of these models, Claude's context window size is 200K" (article 8606394, read 2 Nov 2026). The pricing page lists "Up to 1M" and "varies by model" for every plan. The Max plan article, also labelled "Updated this week", still says "the context window size remains at 200K across all plans" (article 11014257). Two pages against two; the most specific page is recently updated and the pricing page agrees with it, so this unit takes 1M as the window for the four current models in claude.ai chat, and flags it (unsure list, 1).

Three consequences for the course.

  1. The window no longer forces a new chat. On 1M, a chat can run five times longer than B1 §1 assumed before it hits the wall. Every turn still re-sends the whole history (B1 §2; Anthropic's context-window page says the input of each turn "Contains all previous conversation history plus the current user message", Anthropic, Context windows, read 2 Nov 2026). A larger window lets that cost grow further before anything stops it.
  2. The binding limit is attention. The same page, read today: "As token count grows, accuracy and recall degrade, a phenomenon known as context rot. This makes curating what's in context just as important as how much space is available." It adds that "Cached prompt prefixes still occupy the context window: prompt caching changes what you pay for those tokens, not whether they count."
  3. B4 F1's inference no longer follows from its arithmetic. B4 F1 measured the Project knowledge at about 336,000 tokens and concluded, from the retrieval article's rule, that a Project above the 200K window runs in retrieval mode. The retrieval article still ties the switch to the window ("When your project knowledge approaches the context window limit, Claude will automatically enable RAG mode", Claude Help Center, RAG for projects, read 2 Nov 2026, labelled "Updated this week") and gives no threshold. Against a 1M window, 336,000 tokens is about a third of it (arithmetic), so whether that Project ran in retrieval mode is undetermined. F1's fix still stands on the other two grounds B4 gave: what every chat must obey should arrive whole, and every loaded token competes for attention.

B1 §2's caching question

B1 §2 left this to B8: whether, and how, caching reduces what a claude.ai conversation draws from his usage limit. What Anthropic states on 2 November 2026:

  • Project content: yes, by an unpublished amount. "When you add documents to a project, they're cached", and "Every time you reference that content, cached tokens count less than uncached portions toward your usage limits" (Pro article). "Caches expire after a period of inactivity", and "If you come back to a project after a long break, your first message counts that content in full again" (usage limit best practices). Neither page says how much less a cached token counts, or how long the period of inactivity is.
  • Conversation history in a claude.ai chat: not stated. The best-practices article lists "Claude remembers context from earlier in the conversation" under the heading "Our system also includes caching that helps you optimize your limits" and gives no rate and no lifetime.
  • Claude Code on a subscription, which draws on the same limit: yes, and documented. "With prompt caching, Claude Code re-reads that history at the cached token rate, so a one-line question in a session that has been open all day still draws usage for the whole conversation" (Claude Code docs, Manage costs effectively, read 2 Nov 2026). Claude Code requests a one-hour cache for the main conversation "only on a Claude subscription within your plan's included usage", and drops it to five minutes once the session draws on usage credits (Claude Code docs, How Claude Code uses prompt caching, read 2 Nov 2026).
  • On the API, for comparison: cache hits on Opus 5.5 and Sonnet 5.5 cost 0.05 times the base input price, on Fable 5.1 0.025 times, with a five-minute default lifetime and a one-hour option (Anthropic, Prompt caching, read 2 Nov 2026). The page does not mention claude.ai or subscription usage.

So the answer is partial: caching reduces the draw for project content and for Claude Code history; the size of the reduction on his plan, and the lifetime of a claude.ai chat's cache, are unpublished.

02What burns usage for no gain

Anthropic's list of what draws the limit, as read on 2 November 2026: "Message length", "File attachment size", "Current conversation length", "Tool usage (e.g., Research, web search)", "Model choice", "Effort level", "Artifact creation and usage", and "Multi-step tasks, like running code, creating files, or browsing websites" (usage limit best practices). Each of the four habits the brief names spends one of these without buying anything.

Re-reading large files. A file read into a chat is part of the history from then on and is re-sent on every later turn (B1 §2; B4 §3 called this the cost of a cold fetch). Reading it a second time adds a second copy. Anthropic's Pro article names the simplest case: "Don't re-upload files within the same conversation." In Claude Code the documented remedy is to read less in the first place: specific requests let Claude "work efficiently with minimal file reads", and a hook that greps a 10,000-line log for errors cuts the context "from tens of thousands of tokens to hundreds" (Manage costs effectively). In his setup the vault is the large file. The 17 filed units of this course come to 973,729 characters (his setup, counted by script, 2 Nov 2026), about 360,600 tokens at B1 §2's 2.7 characters per token and about 278,200 at the older 3.5: more than the 200K window B1 assumed, about a third of the 1M window (arithmetic). The mean unit is about 57,300 characters, about 21,200 tokens; the largest, B3, about 30,800. A chat that reads whole units to find one section pays for every other section on every turn after.

Giant pastes. Message length is the first item on Anthropic's list, and a paste is re-sent on every turn like a file. Anthropic's own advice cuts the other way for material the task needs: "Provide all relevant data in a single, well-structured message" (best practices, research tasks), and B3 §4 gave the evidence that a brief arriving in pieces does worse than one complete brief. The waste is the paste the task does not need: a whole transcript where the takes for one week would do, a full export where the script needs one column, the same document pasted again in a later turn. The test before pasting is whether the model needs this text to produce this artefact.

Chats that never end. B1 §2's illustrative arithmetic: at about 2,000 tokens an exchange, the 30th turn re-sends about 60,000 tokens of history, and 30 turns send about 930,000 tokens of input in all. Claude Code's documentation names the effect in plan terms: "a one-line question in a session that has been open all day still draws usage for the whole conversation" (Manage costs effectively). On claude.ai, a chat long enough to trigger automatic context management costs more again: "Longer conversations that trigger automatic context management consume more of your usage limit" (article 11647753). And the cost buys worse answers, by context rot (§1).

Re-running research. Research "can use up your limits faster due to Claude retrieving multiple sources" (Claude Help Center, Use research on Claude, read 2 Nov 2026, labelled "Updated yesterday"); Anthropic's engineering team measured its 2025 multi-agent research system at "about 15× more tokens than chats" (Hadfield et al., How we built our multi-agent research system, Anthropic Engineering, 13 Jun 2025, re-read 2 Nov 2026; vendor, 2025 system). Running the same question again pays that again, and B6 §1 adds the second cost: every run produces fresh claims to check, so a re-run doubles the checking as well as the tokens. The fix is DD-B3's rule 8, "an answer worth keeping becomes a file": a fact found once is filed with its source and date, and the next chat reads the file.

Two more items on Anthropic's list belong here. Effort above the task's need: low and medium "work well for routine tasks and stretch your usage further"; higher effort means you "reach your usage limits faster" (effort-settings article). Tools and connectors left on: "Tools and connectors are token-intensive", and the help centre's advice is to turn off web search, Research and connectors a chat does not need (article 11647753). B4 F14 already recommended "On demand" for connectors.

03When a new chat is cheaper

B1 §7 closed with the fix for a buried fact, "trim the window or start a new chat", and handed it to B3, B4, B6 and B8. B4 §4 set out when to start a new chat on grounds of quality and independence. This section adds the cost side.

The mechanism. Continuing a chat re-sends its whole history on every turn. A new chat sends its fixed layers (preferences, project instructions, skill descriptions, memory, connectors) plus whatever he hands it. The fixed layers are paid on every turn of every chat either way, so they cancel out of the comparison; what differs is the history. B4 §3 measured the project instructions at about 1,600 tokens and B5 §3 the 19 skill descriptions at about 2,300; the system prompt, memory and preferences were not measured.

The arithmetic. On B1 §2's assumption of about 2,000 tokens an exchange, 30 turns in one chat re-send about 930,000 tokens of history. The same 30 turns as three chats of 10, each later chat opening with a handoff note of about 2,000 tokens, send 110,000 + 130,000 + 130,000 = 370,000 (arithmetic; turn k of a chat sends the handoff plus 2,000k). That is 60% less history for the same work, provided the later turns needed only what the handoff note carries.

What caching changes. While a cache is warm, re-sent history costs less: on the API, an Opus 5.5 cache hit is 0.05 times the input price (Prompt caching); on his plan the discount exists for project content and Claude Code history and its size is unpublished (§1). So inside one working session, a long chat costs less than the uncached arithmetic says. The comparison flips back after a break. The first message after the cache expires "counts that content in full again" (usage limit best practices, for project content), and in Claude Code "your first message after a break longer than the cache lifetime misses the cache and reprocesses your full context" (Manage costs effectively). Anthropic's own product points the same way: if a long conversation sits idle in a terminal session on the one-hour cache, Claude Code "can compact it shortly before the cache expires", so the summary is written while the history is still cheap to read (How Claude Code uses prompt caching). That is a handoff note, written by the tool.

Trimming. On claude.ai no help article read describes a way to trim a chat by hand; the one trimming mechanism is automatic context management, which summarises earlier messages when code execution is on and "consume[s] more of your usage limit" (article 11647753). In Claude Code there are three documented moves, with different costs (How Claude Code uses prompt caching):

  • /rewind truncates to an earlier turn, a prefix that is already cached, so it is the cheap way to abandon a wrong path.
  • /compact replaces the history with a summary; the summarising request reads the whole conversation, cheaply while the cache is warm, at full price after a break. Anthropic's advice is to run it "at a natural break in your work, such as between tasks".
  • /clear starts fresh: "When you want a fresh start instead of continuity, /clear costs nothing" (Manage costs effectively), and "Stale context wastes tokens on every subsequent message" (same page).

Model and effort. In Claude Code, "each model has its own cache", so a model switch mid-session "recomputes the entire request even when the content is identical"; an effort change does the same "on most models", but on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 with a Claude subscription "the cache stays intact by default". The page's tip is still to "Pick your model and effort level at the top of a session" (How Claude Code uses prompt caching). On claude.ai, Anthropic says he "can change the model, effort level, or thinking setting at any point in a conversation" (effort-settings article) and says nothing about the cache. B2 §7 called the claude.ai effect undocumented; it still is. The Claude Code rule costs nothing to apply on claude.ai too.

The rule, put together (my synthesis; each branch traces to a source above): when the next step does not need this chat's history, a new chat (in Claude Code, /clear). When it does, and he is coming back after the cache has expired, a new chat with a handoff note, since the next message pays the full history anyway and the note is smaller. When it does and the cache is warm, stay; in Claude Code, /rewind off a wrong path and /compact only between tasks; on claude.ai, where no help article read describes a way to trim a chat by hand, a wrong path means a new chat. The cache lifetime on claude.ai is unpublished; Claude Code's documented one hour on a subscription, within the plan's included usage, is the only figure for his plan; a session that draws on usage credits, as Fable does on Pro, drops to five minutes; using the hour for claude.ai is an analogy.

This rule refines B4 §4's third "stay" condition ("Work has paused briefly"): a brief pause is one inside the cache lifetime.

05Privacy and retention: memory, projects, and what lives only in the vault

B4 F15 found private terms in the public build and left the general rules to B8. This section sets them as categories and rules, from what Anthropic says it does with each kind of stored material. No inventory of what he has stored is made here.

What Anthropic keeps, and for how long (as of 2 November 2026)

Chats. The privacy centre's retention page covers Free, Pro, Max and Claude Code on those accounts and is dated 1 July 2026 (Anthropic Privacy Center, How long do you store my data?, read 2 Nov 2026). It gives no fixed period for chats he keeps; personal data is retained "for as long as reasonably necessary". A deleted chat leaves his history at once and back-end storage within 30 days. With the model-improvement setting on, new or resumed chats may be kept de-identified for up to five years in training pipelines; with it off, they are not used for future training, though data already in a training run in progress stays there. A chat flagged for a usage-policy violation keeps its inputs and outputs for up to two years and its classification scores for up to seven. Feedback (a thumbs-up or thumbs-down, or a bug report) keeps the associated data for five years. The August 2025 terms change set the same two branches: five years with training allowed, the existing 30-day retention without it, for new or resumed chats only; it does not apply to Claude for Work, Government, Education or the API (Anthropic, Updates to our consumer terms, 28 Aug 2025, re-read 2 Nov 2026). The setting is a toggle under Settings > Privacy (Anthropic Privacy Center, How do I change my model improvement privacy settings?, dated 3 Aug 2026).

Who can read them. Review happens only when he allows chats to improve Claude; "Access is limited to a small number of personnel involved in model training", and data is de-linked from his user ID before review; chats flagged by safety classifiers "may still be used to improve our internal trust and safety models". The same article advises caution with bank and card numbers, medical records, passwords or login credentials, and confidential business or personal documents (Claude Help Center, I would like to input sensitive data into my chats with Claude, read 2 Nov 2026, labelled "Updated this week").

Memory. "Claude saves memory as a set of individual topics as you chat." Each project has its own memory; in a project, Claude uses that project's memory and his memory from chats outside projects, never another project's; turning off "Use account memory" on the project's page separates them fully. By default memory does not store sensitive topics such as health, politics or religion, unless he opts in; "Some information is never saved to memory, even if you ask": government ID numbers, criminal history, financial account numbers and immigration status. Deleting a chat does not remove the memory entries written from it; they are deleted one by one under Settings > Your Claude, "Manage" next to "Your memory". The article does not say how much memory enters a chat (Claude Help Center, Use Claude's chat search and memory to build on previous context, read 2 Nov 2026, labelled "Updated this week"). The retention page says nothing about memory, projects or uploaded files.

Projects. "Context is not shared across chats within a project unless the information is added into the project knowledge base"; the article describes sharing for Team and Enterprise and says nothing about retention or training for project files (Claude Help Center, How can I create and manage projects?, read 2 Nov 2026).

Incognito. Incognito chats "aren't saved to your chat history or to Claude's memory", are kept 30 days by default, are not used for training, are available only outside projects, and cannot be reopened once closed (Claude Help Center, Use incognito chats, read 2 Nov 2026, labelled "Updated this week").

What follows for each kind of material

Four places can hold what he works with: memory, a Project, the private vault (a private repository, B5 §5), and the public build (B4 F15). Five properties decide which: memory is written by a model and re-inserted in amounts nobody publishes (B1 §7; the memory article above); a Project's output, in the Learning Project's case, is published (B4 F13); a chat's text sits on Anthropic's servers under the retention rules above; a commit to a repository is hard to take back, since GitHub's documentation says removed data may survive in clones, forks and cached views (B4 F15 cites GitHub Docs, not re-checked here); and the public build renders whatever the data files hold (B4 F15).

Three notes on the table. Memory gets only what is already public because nobody can see in advance which chat it will reach, and inside the Learning Project the chats it reaches write published units (B4 F13, whose fix, turning off "Use account memory" for that Project, the memory article confirms still exists). Health stays out of memory by Anthropic's default; opting in under "Include sensitive topics in memory" would send health facts into every chat memory reaches. Employer material goes nowhere in this account: the consumer terms govern Free, Pro and Max, and Anthropic's commercial products are under separate terms (consumer-terms post); work for his employer belongs under whatever terms that employer has set, outside this course. That line is my rule; the sources give the two sets of terms and the caution, and he decides.

Deleting is three steps, and the second is easy to miss. Delete the chat (gone from history at once, from back-end storage within 30 days); delete any memory entries it wrote, since the chat's deletion leaves them; and, where model improvement was on when the chat ran, accept that a de-identified copy may already be in a training run (retention page; model-improvement article). For a one-off question involving private material outside any Project, an incognito chat avoids the first two steps.

Paste after DD-B3's ten operating rules. Each rule names its source; where it refines a DD-B3 rule, it says which. Product facts as of 2 November 2026; re-read the sources at the staleness check.

Usage, limits and privacy (from B8, 2 Nov 2026)

  1. Model and effort are set before the first message and never changed inside a chat. To change either, I start a new chat. In Claude Code a model switch recomputes the whole request, and an effort switch does too on most models, though not on the 5.5 models or Fable 5.1 on a subscription; on claude.ai the effect is undocumented, and the rule costs nothing. (Refines DD-B3 rule 10 and B2's rules for the routing table. Claude Code docs, How Claude Code uses prompt caching.)
  2. One task per chat; a new task gets a new chat (in Claude Code, /clear). Stale context is paid on every later message. (Refines DD-B3 rule 6. Claude Code docs, Manage costs effectively; B4 §4.)
  3. Back to a long chat after a break, I start a new chat with a handoff note. The first message after the cache expires pays for the whole history again; a note costs only itself. Claude Code's cache lasts one hour on a subscription within the plan's included usage, and five minutes on usage credits, as Fable runs on Pro; claude.ai publishes no lifetime, so I treat a break over an hour the same way (analogy). A short pause inside the hour: I stay. (Claude Help Center, Usage limit best practices; Claude Code docs, Manage costs effectively and How Claude Code uses prompt caching; B8 §3.)
  4. A handoff note carries decisions, open items and file paths, never the transcript, and lives in the vault. (DD-B3 rule 8; B4 §4, Anthropic's structured note-taking.)
  5. In Claude Code: /rewind to abandon a wrong path, /compact only between tasks, /clear for a fresh start. Rewind returns to a cached prefix; compacting reads the whole conversation; clearing costs nothing. (Claude Code docs, How Claude Code uses prompt caching and Manage costs effectively.)
  6. I never paste what a chat can read by path, and never re-upload a file in the same chat. A paste or a file is re-sent on every later turn. What the task needs, I give once, whole, in the first message. (Claude Help Center, About Claude's Pro plan usage; Usage limit best practices; B3 §4.)
  7. I read sections, never the whole vault. A chat finds the section a brief points to by search and reads that. The 17 filed units are about 360,000 tokens; one averages about 21,000. (B8 §2 and §4, counted 2 Nov 2026; Claude Code docs, Manage costs effectively, on minimal file reads.)
  8. A fact is searched once, until its staleness check. Found, it is filed with its source and date, and the next chat reads the file; it is searched again only at the six-month staleness check (method §6). Deep research runs once per question, by B6's routing; it costs about fifteen chats of tokens (Anthropic's 2025 figure) and every run brings new claims to check. (Refines DD-B3 rule 8. B6 Deliverable A; Claude Help Center, Use research on Claude; Hadfield et al., Anthropic Engineering, 13 Jun 2025.)
  9. Tools and connectors stay off unless the chat uses them; connectors load on demand. (Supports DD-B3 rule 9. Claude Help Center, Understanding usage and length limits; B4 F14.)
