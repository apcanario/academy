1 · The layers in claude.ai, and what belongs in each

B1 §6 placed each layer in the context window by who writes it and how far it reaches. This section asks the next question: given what each layer is, what should go into it.

Layer Scope When it enters the window What belongs there What does not
Profile preferences Every chat on the account Every chat Rules about him that hold everywhere: tone, format, decision style Anything true only in one Project
Project instructions Chats in one Project Every chat in the Project The few rules that must hold in every chat of the Project, and where everything else is Procedures, lists that change, copies of other files
Project files (knowledge) Chats in one Project Loaded whole while small; searched once near the window limit Reference material every chat in the Project needs whole Records, superseded drafts, build inputs, anything a chat can fetch by path
Memory Account, plus one store per Project Carried into new chats; how much is undocumented Facts about him that come up unprompted Rules, and anything already in a file
Skills Account Name and description every chat; body when a request matches Multi-step procedures for one kind of task Facts and standing rules
Connectors Account All at the start, or on demand, by setting Live access to an outside service Anything a chat never uses
Scheduled tasks Account Their own session, run by run Unattended, repeatable jobs with a clear outcome Work that needs a judgement mid-run

The first three columns are documented; the last two are my synthesis of the sources for each row, as read on 29 October 2026:

Preferences and project instructions. Anthropic's help centre says preferences are "applied to all of your conversations with Claude" and that project instructions "only apply to chats within that project"; it states no order of precedence and says the features can be used "independently or in combination" (Claude Help Center, Understanding Claude's personalization features; product documentation). The projects article says "Claude will use these instructions for all the chats within the project" (Claude Help Center, How can I create and manage projects?). Since no precedence is documented (B1 §6), a rule that the narrower layer must win has to be written into the narrower layer, and ideally into the wider one too. That is the fix in §5.

Project files. "Anything you upload to this space will be used across all of your chats within that project" (projects article). The same article adds the limit that matters for planning: "Context is not shared across chats within a project unless the information is added into the project knowledge base." Two help pages describe how the files reach a chat, and they do not say the same thing.

Where sources disagree. Anthropic's skills article (22 September 2026) says projects "provide static background knowledge that's always loaded when you start chats within them" (Claude Help Center, What are skills?). The retrieval article (10 September 2026) says that "When your project knowledge approaches the context window limit, Claude will automatically enable RAG mode", in which Claude uses a search tool and "retrieves only the most relevant information", and that a project can return to loading everything once its knowledge falls back below the threshold (Claude Help Center, Retrieval augmented generation (RAG) for projects). Read together: "always loaded" holds only below the threshold. Above it, project files are searched, and a chat sees the passages the search returns.

Memory. Claude "saves memory as a set of individual topics as you chat"; each project has its own memory, and inside a project "Claude uses the project's memory alongside your memory from chats outside of projects"; a project can be kept fully separate by turning off "Use account memory" on its page (Claude Help Center, Use Claude's chat search and memory to build on previous context). The article does not say how much of memory enters a given chat. B1 §3 covers what memory stores and excludes.

Skills. Anthropic's developer documentation gives the loading rule: a skill's name and description are loaded at startup into the system prompt, at about 100 tokens per skill; the body of SKILL.md, under 5,000 tokens, enters the window only when a request matches the description; bundled files cost nothing until read (Anthropic, Agent Skills; product documentation). The help centre draws the boundary between layers in one sentence each: custom instructions "apply broadly to all your conversations", projects hold "static background knowledge", and skills "are task-specific and only load when relevant, making them better for specialized workflows" (What are skills?). The help page on using skills says Claude "automatically identifies and loads relevant skills based on your task" and does not say whether a skill can be switched on for one Project only (Claude Help Center, Using skills in Claude). On what he can read today, skills are an account-wide layer.

Connectors. "Each connector takes up space in a conversation." Three modes are documented. In "Auto", the default, "Claude decides dynamically which connectors to load based on what you're working on". In "Always available" mode, "All your connectors are loaded at the start of every conversation"; in "On demand" mode, "Connectors aren't loaded until Claude searches for the right one based on your request"; on-demand loading is recommended for libraries of ten or more connectors or when conversations hit length limits (Claude Help Center, Manage Claude's tool access, 16 March 2026). The usage article adds: "Tools and connectors are token-intensive" (Claude Help Center, usage and length limits).

Scheduled tasks. Anthropic documents several kinds (Cowork, Claude Code cloud, Claude Code desktop and in-session); two matter here. In Cowork, "Each scheduled task runs as its own Cowork session", with connected tools, skills and plugins (Claude Help Center, Schedule recurring tasks in Claude Cowork). In Claude Code, a cloud scheduled task is "a saved Claude Code configuration: a prompt, one or more repositories, and a set of connectors"; each repository is cloned at the start of every run; each run opens as a new session; the documentation says "the prompt must be self-contained and explicit about what to do and what success looks like"; runs draw on his subscription usage, and schedules more frequent than hourly are rejected. The feature is labelled research preview (Claude Code docs, Automate work with scheduled tasks; product documentation). B1 §7 drew the consequence: a scheduled task knows nothing of the chat that created it. B5 covers what a task can and cannot touch.

The Claude Code documentation states the dividing rule for its own equivalent of project instructions in terms that transfer: keep the instruction file "to facts Claude should hold in every session", and "If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill" (Claude Code docs, How Claude remembers your project; vendor guidance written for CLAUDE.md). Applying it to claude.ai project instructions is my analogy, as B1 §2 applied the same page's size guidance.

2 · Hot, warm and cold: why the vault/index split exists

The brief's word "temperature" needs a definition before it can be used. In this unit:

  • Hot is text placed in the window at the start of every chat: preferences, project instructions, skill descriptions, connectors in "Always available" mode, and project files while the Project is below the retrieval threshold.
  • Warm is text a search pulls in when a request seems to need it: project files in retrieval mode, memory, chat search, connectors and skills on demand.
  • Cold is text outside the window until a chat fetches it by name: files in the repository, read by path after a clone.

The labels are mine. Anthropic's engineering team describes the same choice as context loaded up front against context retrieved just in time: an agent can "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and load the data only when it needs it; its recommended middle course is a hybrid, "retrieving some data up front for speed, and pursuing further autonomous exploration at its discretion"; and Claude Code is its worked example, where "CLAUDE.md files are naively dropped into context up front" while "primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time" (Anthropic, Effective context engineering for AI agents, 29 Sep 2025; vendor guidance).

His method already has that shape, and the reason is size. The method states where things live: everything is in the private repository; the Project "holds mirrors of docs/"; and "A chat clones the repo and ends with a commit" (method.md, Home). The vault, courses/, holds the finished units; courses-index.md holds, for every unit, its status, model, search flag and path. In the engineering post's terms the index is a file of lightweight identifiers, and the vault is what they point to.

The split is forced by arithmetic. The seven filed Brand + AI units in the vault come to 358,052 characters, and the 137 history reports in kit/greece/ and kit/rome/ to 3,484,164 (Unicode characters, both counted by script on 29 October 2026). At B1 §2's arithmetic of about 2.7 characters per token, the history reports alone are about 1.3 million tokens, more than six times the 200K window he has on claude.ai (B1 §1). No chat can hold the course; every chat can hold the map to it. B1 §7 put it as the vault being "the one store that never enters a chat by itself", fetched when a chat needs a file, and handed the question of which file belongs at which temperature to this unit.

The answer the evidence supports:

  1. Hot: what every chat must obey whole. The rules (method, sourcing standard, reader), the map (the index) and the queue (the backlog). A checklist read in fragments is a different checklist; these files need to arrive whole, which only happens while the Project stays under the retrieval threshold (§1).
  2. Warm: facts about him that come up unpredictably. That is what memory is for (§1).
  3. Cold: everything a chat can name before it needs it. Units, reports, syllabi, research, audits, build code, records. The index names each one's path, so a chat that needs a unit can read it after cloning.

The Deliverable measures how far the Project has drifted from this, and the drift is large: the method says the Project mirrors docs/, while SETUP.md §2 tells him to upload the filed units, the superseded research and its five notes, the history kit's briefs and rubrics, the Rome syllabus, the theme and the Brand + AI data files as well.

3 · What loads every turn, what loads on demand, and what each costs

B1 §2 gave the mechanism: the model keeps nothing between turns, every turn re-sends the whole chat, and so every hot layer is paid once per turn, on every turn. On claude.ai the payment is drawn from his usage limit, and Anthropic's usage guidance names "Current conversation length" among the factors that draw it down (Claude Help Center, Usage limit best practices, 22 Sep 2026). B2 §2 reported the one documented relief: project content is cached and counts less when reused. Anthropic's page adds that caches expire after inactivity, so the first message after a long break counts the content in full again.

The project files are no longer hot. 907,260 characters is about 336,000 tokens at B1's 2.7 characters per token, and about 259,000 at the older 3.5 figure B1 also reports. Both exceed the 200K window. On the retrieval article's rule, a Project of that size runs in retrieval mode (RAG for projects). I cannot see the mode from the repository, so this is an inference from the documented rule and the measured size. What was observed is consistent with it but does not test it, since both observations come from Claude Code sessions, which list the Project's documents by name whatever their size (unsure list, 1): in B1's writing session a list of 24 documents arrived by name and five were then read in (B1 §1, observed 28 October); in this unit's session, a list of the Project's 33 documents arrived by name with an instruction to read or search them with a tool (observed, 29 October 2026).

That changes what the Project knowledge is worth. In retrieval mode the method arrives as whatever passages a search returns for the request at hand. The sourcing checklist, which only works when every item is checked, may arrive as two items out of twelve. And the search runs over everything in the knowledge, including the superseded research that failed Audit 1 on 23 of 91 claims (courses-index.md) and that covers the same topics as the units that replaced it. B1 §2 reported Chroma's vendor finding that distractors, passages similar to the answer, lowered accuracy further; a superseded draft of the same material is a distractor in that exact sense.

What each kind of loading costs, in his terms:

  • Hot costs tokens on every turn of every chat, and attention (B1 §2). It buys certainty that the text is there. It is worth it for the instructions, which are small, and for files every chat needs whole.
  • Warm costs little until used, and costs reliability: the text is present only if a search or a match brings it in. Skill bodies are warm by design, and a procedure that fires on a recognisable request belongs there. Rules that must hold everywhere do not.
  • Cold costs a deliberate fetch, a tool call that adds the file to the window from then on (B1 §7). It buys a clean window: nothing arrives that the chat did not name.

4 · When to start a new chat, and when not to

Start a new chat when one of these holds.

  1. The task changes. B3 §5 gave the evidence for one artefact per prompt: each task's material is irrelevant context for the others, and the tasks want different models. A new task in an old chat carries the old task's material on every turn (§3).
  2. The first output missed. B3 §4 reported Laban and colleagues' finding that a brief arriving in pieces does worse than one complete brief, and the paper's own advice to consolidate the requirements into one instruction and start a new conversation. Rewrite the brief and open a new chat.
  3. The chat is long. Every turn re-sends everything before it (B1 §2). Anthropic's advice: "Try starting a new conversation if you're approaching your usage limit in a longer chat" (usage and length limits). When code execution is on, long chats are also summarised automatically, and summarising is lossy by definition (B1 §3).
  4. The next step must not see this one. A checker or auditor that watched the unit being written is no longer independent. B2 §8 gave the evidence on self-preference, and the method requires a fresh checker "in a new chat that has not seen the unit written" (method.md §5).
  5. A unit starts. "Never reuse a chat across units; leaked context is how a course starts repeating itself" (method.md §4).

Stay in the chat when one of these holds.

  1. The next step works on material only this chat has. Applying a checker's findings as exact replacements, finding by finding, needs the current text and the finding list together. Moving them to a new chat means pasting both again, and the paste is the same tokens plus a chance to paste the wrong version.
  2. The step is a short follow-up on the same artefact, for example a second pass on a caption, where the earlier output is the material.
  3. Work has paused briefly. Anthropic's usage guidance says cached project content counts less when reused and that the cache expires after inactivity (usage best practices). Whether starting a new chat in the same Project loses that cache is undocumented.

Whichever way it goes, a chat ends by writing its state somewhere a later chat can read. Anthropic's engineering post calls this structured note-taking and gives the example of "your custom agent maintaining a NOTES.md file"; its other technique for long work is to give "specialized sub-agents" focused tasks "with clean context windows" (Effective context engineering). His method already does both. The backlog and changelog are the notes file (method.md §8), and one chat per unit, with the checker in its own chat, is the clean window. The weak point is the first: a new chat knows only what the last one wrote down. The Deliverable's finding F10 shows the notes are already a step behind.

5 · How a project rots, and how to stop it

A project rots when the text the model reads stops matching the work. The three kinds the brief names each have a documented mechanism.

Stale files. A file that was right when written and was never retired keeps arriving. Anthropic's usage article recommends removing project files no longer in use (usage and length limits). Claude Code's documentation lists what its own instruction audit looks for, among them "instructions written for older models, references to files or commands that don't exist, and files that contradict each other" (Claude Code docs, Memory; vendor guidance for Claude Code). His repository has all three: a hand-off note headed "Start here" that tells the next session to create a repository that now exists; a data file that still tells a chat to run audits "in the personal-assistant Project"; and two files that still tell the reader to run a build script retired on 28 October (Deliverable, F9).

Duplicated rules. A rule written in two places is paid twice where both are hot, and it drifts as soon as one copy is edited. Copies that are identical can be caught by a script. The dangerous ones are paraphrases, because no comparison flags them. His project instructions share only 20 eight-word sequences with method.md, 3% of their own, yet their Review and Backlog paragraphs restate §6 and §8 of the method in other words. The list of which units are written with search on exists in four prose copies, in three different versions (Deliverable, F8). B1 §6 flagged the tone rules repeated in his preferences and his project instructions.

Instructions that contradict preferences. Claude Code's documentation: "if two instructions contradict each other, Claude may pick one arbitrarily", followed by the advice to review periodically "to remove outdated or conflicting instructions" (Claude Code docs, Memory). The claude.ai help centre states no precedence between preferences and project instructions (personalisation features), so the Claude Code sentence is the nearest documented description of what happens; applying it to claude.ai is my analogy, as in B3 §4. B3 §4 named one conflict: the preferences send anything with three or more sections to an HTML artifact, and a unit is a Markdown file. The Deliverable finds two more of the same kind (F5).

Three habits stop rot, and each traces to the sources above.

  1. One home per rule, and pointers everywhere else. The method already applies this to course content ("each anecdote, dispute and self-test question has one home; the others point to it by number", method.md §3). Applied to rules, a fact such as which units search lives in one place (the index's Search column, which kit/index_check.py already checks against the data file) and every other mention points there.
  2. The narrower layer names its exceptions. Since no precedence is documented, the Project instructions state where the Project departs from the preferences, in one paragraph.
  3. A scheduled check. Rot accumulates between sessions, and nobody reads a file to look for it. The checks in the Deliverable are mechanical, which is the kind of work Anthropic's documentation describes scheduled tasks for: "unattended, repeatable, and tied to a clear outcome" (scheduled tasks).
