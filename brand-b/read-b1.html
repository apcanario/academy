01The context window is the one thing you control

Anthropic defines the context window as all the text a language model can reference when generating a response, including the response itself, and separates it from the corpus the model was trained on: the window is the model's "working memory" (Anthropic, Context windows). Everything in a request counts against it: the system prompt, every message (tool results, images and documents included), the tool definitions, and the output, extended thinking included (same page).

That is the whole interface. The model's trained parameters are fixed when he uses it; Anthropic's claude.ai system prompt is written by Anthropic (Anthropic, System prompts release notes). Everything else that reaches the model reaches it as text placed in that window, and almost all of that text is his choice: the preferences he saved, the project instructions, the files he put in the Project, which skills are installed, whether memory is on, what he pastes, what he attaches, and when he starts a new chat. A better answer comes from a better window. There is no other lever.

How big the window is (as of 28 Oct 2026). Two different numbers are in circulation, and the one that applies to him is the smaller.

  • On the API, Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 all have a 1M-token window with up to 128K output tokens per request (Anthropic, Context windows; Anthropic, Models overview).
  • On claude.ai paid plans, Anthropic's help centre states that the context window is 200K tokens across all models and paid plans, with some models at 500K on Enterprise (Claude Help Center, usage and length limits).

His Project runs on claude.ai, so his working budget is 200K tokens, a fifth of the figure on the model page. (On 2 Nov 2026 Anthropic's pages disagree on the claude.ai window, and the most specific gives 1M for the current models in chat: B8 §1.)

Worked example: what the chat that wrote this unit received (observed, 28 Oct 2026). Before the brief arrived, the window already held Anthropic's system prompt; his saved preferences; the Learning Project's instructions; a snapshot of his memory (a profile, a preferences line and a listing of memory file paths with one-line descriptions); and the names and one-line descriptions of his fifteen plugin skills. The brief came next. During the work, a list of the Project's 24 documents arrived by name, then five of them (method.md, sourcing-standard.md, courses-index.md, reader.md, units_data.py) and about twenty web pages were read in. Each of those reads added text to the same window. None of it was "known" to the model before it was placed there.

02Tokens: what he pays with and what the model attends with

What a token is

A token is the smallest unit the model works in: a word, part of a word, a character or a byte. For Claude, the number of characters per token depends on the model and the language. On models before Claude 4.7, a token is about 3.5 English characters; Claude 4.7 and later models use a newer tokenizer that produces about 30 percent more tokens for the same text (Anthropic, Glossary). Opus 5.5 is in the later group, so on Anthropic's two figures an English token is roughly 3.5 ÷ 1.3 ≈ 2.7 characters. That is arithmetic on the glossary's numbers; nobody measured it, and the glossary gives no figure for Portuguese; for an exact count Anthropic points to its token-counting endpoint (same page).

On that arithmetic, a 200K-token window holds roughly 540,000 characters of English. This unit, at about 36,000 characters, would be about 13,000 tokens: around 6 to 7 percent of his window, before anything else is loaded.

Tokens as cost

On the API, price is per million tokens, with output dearer than input. As of 28 October 2026: Opus 5.5 $4 input / $20 output; Sonnet 5.5 $2 / $10; Haiku 5.5 from $0.10 / $0.50; Fable 5.1 $10 / $50 (Anthropic, Models overview). Which model to route each task to is B2.

The mechanism that matters more than the price list is that the model keeps nothing between turns. Anthropic's API documentation says the Messages API is stateless and that the full conversation history is sent with every request (Anthropic, Working with messages). The context-window page says the same in turn-by-turn terms: each new turn's input contains all previous conversation history plus the new message, and each response becomes part of the input for the next turn (Anthropic, Context windows).

The consequence is quadratic. Illustrative arithmetic, unmeasured: if every exchange adds about 2,000 tokens, the 30th turn sends about 60,000 tokens of history, and the 30 turns together send about 2,000 × (1 + 2 + … + 30) = 930,000 tokens of input, plus every fixed layer (preferences, project instructions, memory, skill descriptions) once per turn. The thirtieth turn sends thirty times the history of the first, whatever the length of the question itself.

On claude.ai he does not see token prices; he sees a usage limit. Anthropic says usage depends on the length and complexity of conversations, the features used and the model, that claude.ai, Claude Code and Claude Desktop share one limit, and that tools and connectors are token-intensive (Claude Help Center, usage and length limits). On the API, a repeated prefix can be cached: cache reads on Opus 5.5 are priced at 0.05 times the base input price, with a default five-minute cache lifetime (Anthropic, Prompt caching). Whether, and how, caching reduces what a claude.ai conversation draws from his usage limit is not stated in the help articles cited here. Treat it as unknown here; B8 §1 gives what Anthropic states, and B8's deliverable the usage rules.

Tokens as attention

The transformer architecture that large language models are built on uses self-attention, a mechanism that relates every position in a sequence to every other position when computing each output (Vaswani et al., Attention Is All You Need, NeurIPS 2017). Anthropic's engineering team draws the practical consequence: with n tokens there are n² pairwise relationships, so the model has a finite "attention budget" that each new token draws down, and context is "a finite resource with diminishing marginal returns" (Anthropic, Effective context engineering for AI agents, 29 Sep 2025). Anthropic's own documentation names the effect: as the token count grows, accuracy and recall degrade, which it calls context rot, and it concludes that what is in context matters as much as how much fits (Anthropic, Context windows).

Three bodies of evidence stand behind this, and they do not measure the same thing.

  • Peer-reviewed. Liu and colleagues found that models performed best when the relevant information sat at the beginning or the end of a long input, and noticeably worse when it sat in the middle, including models built for long contexts (Liu et al., "Lost in the Middle", TACL 12, 2024, 157–173). The models tested date from 2023.
  • Vendor research. Chroma tested 18 models from four families, Claude Opus 4, Sonnet 4, Sonnet 3.7, Sonnet 3.5 and Haiku 3.5 among them, and found performance growing less reliable as input length grew, even on simple retrieval and copying tasks; distractors (passages similar to the answer) lowered accuracy further, and the degradation was not uniform across positions or tasks (Hong, Troynikov and Huber, Context Rot, Chroma, 14 Jul 2025). Chroma publishes this on the site of its own retrieval-database product, so it has an interest in the conclusion; label it vendor data.
  • Platform statement. Anthropic states the degradation as a property of its models generally, without a figure (Anthropic, Context windows).

Where they differ: Liu et al. report a U-shape by position on 2023 models; Chroma reports that position, similarity and distractors interact and that the curve is not a clean U. None of the three measured Opus 5.5. The direction is consistent across all three: more text in the window, less reliable use of any one piece of it. The size of the effect on his model is unmeasured.

For his Project this means the 24 documents, the memory snapshot, the preferences, the project instructions and fifteen skill descriptions all draw on the same budget as the brief they are meant to support. Anthropic's guidance for the equivalent file in Claude Code is explicit: target under 200 lines per instruction file, because longer files consume more context and reduce adherence (Claude Code docs, Memory). That guidance is written for CLAUDE.md; applying it to project instructions is my analogy, and the claude.ai help centre states no such limit. What belongs in which layer is B4.

03What persists: within a chat, across chats

Within a chat

Inside one chat, everything persists because everything is re-sent. Previous turns are preserved completely and accumulate in the window (Anthropic, Context windows). On Opus 5.5 that includes its own previous thinking: Opus 4.5 and later Opus models keep earlier thinking blocks by default, and those count against the window like any other input (same page).

Within a chat, a fact can be lost in two ways.

  1. It is still in the window but not used. That is the attention problem in §2. A rule stated in turn 3 of a 40-turn chat is present and competing with everything after it.
  2. It is summarised away. On claude.ai, when code execution is enabled, long chats trigger automatic context management: Claude summarises earlier messages to continue. The help centre says the full history is preserved so earlier content can still be referenced, and that such long chats consume more usage, so a new chat may help (Claude Help Center, usage and length limits). In Claude Code the equivalent is compaction: after /compact, the root CLAUDE.md is re-read from disk and re-injected, and an instruction that vanished after compaction had usually been given only in the conversation (Claude Code docs, Memory).

Across chats

Across chats, nothing persists in the model. A new chat is a new request with a new window, built from whatever the product places in it. Claude Code's documentation states it plainly: each session begins with a fresh context window, and two mechanisms carry knowledge across sessions, the CLAUDE.md files he writes and the auto-memory notes Claude writes, both loaded at the start of every session (Claude Code docs, Memory). claude.ai works on the same principle with more layers:

  • Profile preferences ("Instructions for Claude") are account-wide and applied to all conversations (Claude Help Center, personalisation features).
  • Project instructions apply only to chats within that project (same article).
  • Project files sit in project knowledge; when that knowledge approaches the window limit, claude.ai switches the project to retrieval mode and pulls only the most relevant parts into the chat (Claude Help Center, RAG for projects, 10 Sep 2026).
  • Memory is written as individual topics while he chats, and an update made in one chat is picked up in the next. Each project has its own memory; inside a project Claude uses that project's memory plus his account memory from non-project chats, never another project's (Claude Help Center, chat search and memory). By default it does not store sensitive topics; it never stores government ID numbers, criminal history, financial account numbers or immigration status; deleting a conversation does not delete the memories written from it; incognito chats are excluded (same article).
  • Chat search retrieves past chats by retrieval-augmented search, visible as a tool call; it searches all chats outside projects, and project chats only within their own project (same article).

Each of these is text that something re-inserts. Remove the re-insertion and the fact is gone.

One route does run from his chats into a model, and it is slow. Since Anthropic's consumer-terms change of 28 August 2025, Free, Pro and Max users choose whether new or resumed chats may be used to improve Claude; opted-in data is retained for five years, otherwise 30 days (Anthropic, Updates to our consumer terms, 28 Aug 2025). That feeds a future training run. None of the documentation cited here describes any path by which a chat changes the model he talks to the next morning.

"It forgot" usually means "it was never told"

When a new chat ignores something he said last week, the fault is almost always in one of the re-insertion layers: the fact was said in a chat inside another project; memory did not write it, or wrote a different version of it; chat search was not triggered; the project switched to retrieval and pulled other passages. The diagnostic question is: which layer was supposed to carry this into the window, and did it?

His own rules already encode this. His "Teresa" disambiguation lives in the preferences, the layer present in every conversation. The method's rule of one chat per unit exists because everything earlier in a chat conditions what comes later, which the method describes as leaked context making a course repeat itself (method.md §4). Both are correct applications of the model above.

04Three kinds of knowledge: trained, retrieved, in the conversation

Trained

Claude is built on a model pretrained on a large corpus to predict the next word, then fine-tuned and trained with human feedback to act as an assistant (Anthropic, Glossary). What it learned this way stops at a cutoff. As of 28 October 2026, Anthropic lists the reliable knowledge cutoff of Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 as June 2026 (Anthropic, Models overview). Today is four months past that.

The reader profile in his own brief shows the gap. "Ended competitive karate after the WIKF Global Cup (Oct 2026)" describes an event after the cutoff. No amount of training covers it; the model knows it only because the brief and his memory put it in the window. The same holds for any model lineup, price or plan limit dated after June 2026, which is why B2 and B8 are flagged to search before writing.

Retrieved

Retrieval-augmented generation fetches material at runtime and passes it into the context window with the question, so that the answer is grounded in evidence; the model may fetch it itself through a tool (Anthropic, Glossary). In his setup that covers web search, chat search, a Project in retrieval mode, a file pulled in from GitHub, and Claude Code reading a file. Retrieval is selection: the model sees the chunks that were fetched and nothing else. A Project in retrieval mode can hold up to ten times more, because it no longer loads everything (Claude Help Center, RAG for projects); the price is that the answer depends on what the search returned.

In the conversation

Whatever he typed, pasted or attached, plus everything the model itself wrote earlier in the chat. The second half is easy to miss. Each response becomes input to the next turn (Anthropic, Context windows), so a wrong figure the model produced at turn 5 is in the window at turn 25, read on every turn like anything else there.

Why the distinction matters

The three kinds look identical in the output. A sentence about the 2026 WIKF results reads the same whether it came from a page fetched ten seconds ago, from memory written last week, or from nowhere. The only way to tell is to know what was in the window, which is what the sourcing standard forces: a claim that points to a fetched source can be checked; a claim that points to nothing came from training or was invented. How models fail when they answer from training (confident, specific, wrong) is B6.

05Why the same prompt gives different answers

Sampling is the design

At each step the model produces a probability distribution over possible next tokens, and one is drawn. Temperature controls how random that draw is: higher gives more varied output, lower gives more conservative, more probable phrasing (Anthropic, Glossary). Sampling is deliberate. Holtzman and colleagues showed that always choosing the most likely continuation produces bland, repetitive, degenerate text, and that sampling from a truncated distribution ("nucleus sampling") produced text closer to human writing (Holtzman et al., "The Curious Case of Neural Text Degeneration", ICLR 2020). Temperature is an API parameter; none of the claude.ai help articles cited in this unit offers him a temperature setting.

Even fixed settings vary

Anthropic states that even with temperature set to 0, results will not be fully deterministic, and identical inputs may produce different outputs across calls, on its own service and through cloud providers (Anthropic, Glossary). Anthropic does not give the cause there. A lab study gives one candidate: Horace He at Thinking Machines sampled 1,000 completions at temperature 0 from an open-weights model (Qwen3-235B) and got 80 distinct completions; the most common appeared 78 times, and they first diverged at token 103. He traced the variation to computations whose results depend on batch size, which changes with server load; with batch-invariant kernels all 1,000 were identical (He, Defeating Nondeterminism in LLM Inference, Thinking Machines Lab, 10 Sep 2025). That is a lab blog post, not peer-reviewed, on a non-Anthropic model and serving stack; whether the same cause dominates on Anthropic's service is not stated by either source.

The divergence point is the useful detail. Once one token differs, every later token is conditioned on a different history, so a small difference early becomes a different answer.

In his setup, the prompt is rarely the same

The more common reason two runs differ is that the window differed. Between two chats with the same typed prompt:

  • the system prompt carries the current date and is periodically updated (Anthropic, System prompts release notes);
  • memory may have been updated in between (Claude Help Center, chat search and memory);
  • chat search and project retrieval may return different passages (same; RAG for projects);
  • Opus 5.5 uses adaptive thinking, always on, so the amount of reasoning in the window varies with the request (Anthropic, Models overview).

What this means for checking. One good answer is one draw. It shows the window can produce a good answer; how often it does stays unknown until there are more draws. That is the mechanism behind sampling-based audits; the protocol is B6.

06System prompt, project instruction, user message

All three are text in the same window. They differ in who writes them, where they sit and how far they reach.

Layer Written by Reaches Source
claude.ai system prompt Anthropic Every claude.ai chat; not the API System prompts
Profile preferences Him All his conversations Personalisation
Project instructions Him Chats in that Project only Personalisation
Skill name + description Skill author Every chat where installed; body loads on trigger Agent Skills
User message Him This turn, then every later turn of the chat Context windows

The system prompt sets the frame. Anthropic publishes the claude.ai version and says it supplies current information such as the date at the start of every conversation, encourages certain behaviours, is updated periodically, and does not apply to the API (Anthropic, System prompts release notes). On the API, the developer writes the system prompt, and a system message added mid-conversation carries the same authority as the one at the start (Anthropic, Working with messages). Authority comes from the role the text is given; arrival time leaves it unchanged.

Project instructions and preferences are his standing orders at two scopes. Anthropic's help centre says the features can be used "independently or in combination" and states no order of precedence between them (Claude Help Center, personalisation features). His preferences and the Learning Project's instructions both set tone rules (no flattery, no filler, no preamble). Repeating a rule in two layers spends tokens twice; two layers that disagree leave the model to resolve the conflict with no documented rule. That is a project-rot risk, and B4 audits it.

Skills sit across the layers. Only each skill's name and description load at startup, about 100 tokens a skill, placed in the system prompt; the SKILL.md body (under 5K tokens) enters the window only when a request matches the description, and bundled files only when read (Anthropic, Agent Skills overview). The description is what a request is matched against (same page). His fifteen plugin skills therefore cost about 1,500 tokens in every chat, on Anthropic's per-skill figure, and they fire on their descriptions alone. His decompression skill lists "Netflix" and "dinner" among its triggers (observed), so it becomes a candidate to load whenever those words appear, whatever the conversation is about.

The user message is the request itself, and once sent it is part of the history re-read on every later turn (§3).

None of these is enforced. Claude Code's documentation says Claude treats its instruction files as context and that they are not enforced configuration; to block an action regardless of what Claude decides, it points to a hook; and it says the more specific and concise the instructions, the more consistently Claude follows them (Claude Code docs, Memory). Every instruction layer raises the probability of a behaviour. None guarantees it. How to write instructions that hold is B3.

Notes on the rows that behave differently from what their names suggest:

  • Memory. Memory is notes written by a model about his chats, then re-inserted. It is subject to every failure in this unit: it can be incomplete, outdated or slightly wrong, and it competes for attention like any other text. Facts said only in another Project's chats are not available here (Claude Help Center, chat search and memory).
  • GitHub vault. The vault is the one store that never enters a chat by itself. On claude.ai, files reach a chat or project only when selected; project sync is manual ("Sync now"); and the help centre states the repository must fit within the context window (Claude Help Center, GitHub integration). His method already splits on this line: the Project holds the method and the index; the finished units, which no chat needs all at once, stay in the vault and are fetched when a chat needs one. Which file belongs at which temperature is B4.
  • Scheduled tasks. Each run opens as a new session; the saved prompt is the run's assignment, and Anthropic's documentation says that prompt must be self-contained and explicit because the task runs autonomously (Claude Code docs, Scheduled tasks). A scheduled task knows nothing of the chat that created it.
  • Claude Code. Each session starts with a fresh window; CLAUDE.md and the first 200 lines or 25KB of auto memory load every session (Claude Code docs, Memory). His CLAUDE.md in a repo is the Claude Code equivalent of project instructions and preferences combined.

Reading a bad output

When an answer is wrong, the model above gives four places to look, in this order:

  1. Was it in the window? If the fact lives only in a past chat, another Project, the vault or his head, the model never had it (§3, §4).
  2. Was it buried? If it was there, how much else was there with it, and where? Long windows degrade recall (§2).
  3. Did it come from training? If no source was in the window, the answer came from trained knowledge, which stops at June 2026 (§4).
  4. Was it one draw? Run it again in a fresh chat. If the answers differ materially, neither is reliable on its own (§5).

Each question has a different fix: put the fact into a layer that re-inserts it; trim the window or start a new chat; supply the source; sample before trusting. B3, B4, B6 and B8 take these one at a time.

08DeliverableHow Claude works, in five minutes

Claude doesn't remember anything. Every time I send a message, the app sends Claude a single long piece of text, and Claude writes its reply by reading that text from the top. That text is called the context window. It holds Anthropic's own instructions, my standing instructions, the files in whatever project I'm working in, some notes the app keeps about me, the whole conversation so far, and my new message. Claude reads all of it, writes a reply, and then keeps nothing. When I send the next message, the whole lot is sent again with the new message added at the end.

So the only way to change what Claude does is to change what's in that text. The model itself is fixed. It was trained on a huge amount of writing to predict the next word, then trained further to behave like an assistant, and what it knows from that training stops around June 2026. Anything that happened after that, it only knows if something puts it in the window: me telling it, a web search it runs, or the notes the app keeps.

Those notes are what the app calls memory. As I chat, it writes down facts about me and my projects, and at the start of a new chat it puts those notes back into the window. That's the only reason it seems to remember. If something I said never made it into the notes, or I said it inside a different project, a new chat has never heard of it. When it "forgets", it was usually never told.

The text is measured in tokens, which are chunks of a few letters each. Tokens are what it costs. Because the whole conversation is re-sent every time, a long chat gets more expensive with every message: by the thirtieth message, it is re-reading thirty messages' worth of history to answer one. Tokens are also attention. The more text there is, the less reliably Claude uses any one piece of it, especially things buried in the middle. A short, clean window gives better answers than a long, cluttered one. That's why I start a new chat for each piece of work.

The same question can get different answers. Claude draws each next word from the likely options, because always picking the single most likely one produces flat, repetitive writing. And even when the settings are fixed, the servers don't give exactly the same result every time. On top of that, two chats are rarely identical: the date has changed, the notes have been updated, a search found different pages. Once one word differs, everything after it can go a different way. So one good answer shows it can get it right; it says nothing about how often. For anything that matters, I check a sample of its claims against the sources before I trust the rest.

Different instructions sit at different levels. Anthropic writes instructions that go into every chat. I have preferences that go into every chat I have. Each project has its own instructions that go only into chats in that project. Then there's what I type. All of it is just text in the same window. None of it is a hard rule; it makes the behaviour I want more likely, and the shorter and more specific it is, the more reliably it's followed.

My setup is a set of ways to put the right text in front of it. The course project holds the method and the index, so every chat starts with them. Skills are saved procedures: Claude sees only a one-line description of each, and loads the full instructions when a request matches. The finished units live in a GitHub folder that Claude only sees when I bring files in. Scheduled tasks start a fresh chat each time with a saved prompt and nothing else. Claude Code does the same in a code folder, with an instructions file it reads at the start.

If it gets something wrong, I ask four things. Was the fact in the text it was given? Was it buried under everything else? Did it answer from its training instead of a source? Did I just get one unlucky draw? Each one has a different fix.
